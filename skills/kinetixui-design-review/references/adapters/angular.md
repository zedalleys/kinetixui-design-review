# Adapter: Angular

1. **Detect.** `@angular/core` in `package.json`, `angular.json`/`project.json`, `*.component.ts`, standalone components, `ng-package.json` for libraries.
2. **Where to look.** Component classes (`@Component`, `input()`/`@Input`, `output()`/`@Output`, signals), templates (inline or `.html`), component styles and `ViewEncapsulation`, library entry points (`public-api.ts`), directives, content projection (`ng-content`), DI tokens for configuration (direction, theme), `*.spec.ts`, docs/example components.
3. **Static inspection (V1).** Leads: host-attribute bindings vs inputs (`[attr.x]` on a component host does **not** set an input, and a name set only on the host may never reach the inner control); inputs with `alias`; `host` metadata bindings; `ChangeDetectionStrategy`; `innerHTML` bindings; missing `track` in `@for`/`trackBy`; subscription leaks; direct `document` access instead of injected services; styles piercing encapsulation (`::ng-deep`); `@HostListener` on global targets.
4. **Runtime / gated (V2–V3).** Gated: `ng test`/project test runners, `ng lint`, library build (`ngc`) — only if dependencies exist and the run is safe. Runtime: `ng serve`/built preview in a browser (see web adapter); inspect the inner element's computed accessible name, not just the host.
5. **Idiomatic checks.** Content projection and slots (not React-style render props); signals/inputs/outputs; injection tokens for cross-cutting configuration; `OnPush` where appropriate; native elements inside the component for semantics; a component host should not carry semantics the inner control needs.
6. **False positives.** `::ng-deep` used deliberately for third-party content; `any` in test utilities; absent `OnPush` in small components without a measured cost.
7. **Verification ceiling.** Source → V1. Spec/build runs → V2. Rendered app → V3. Component-host vs inner-element accessible names are only trustworthy at V3 or via a test asserting the inner element.
